# feature —— LocalLrcPlayer 规范开发流程

这是一个纯本地、零依赖的开发工作流。目标是把"想清楚再动手、动完必验证、验证完更新文档"固化下来, 契合本项目单人维护 + 手工 swiftc 构建 + 中文文档的现实。

严格按下面 6 个阶段推进。除非用户明确说"跳过", 否则不要略过任何阶段。每个阶段结束后用一句话报告状态再进入下一阶段。

## 阶段 0 · 读上下文(动手前必做)

不要凭记忆或直接反推代码就开工。先读:

- `ROADMAP.md` —— 计划中的功能 + 已知 bug, 确认这次改动是否已在计划里、有没有相关坑。
- `HANDOFF.md` —— 跨工具交接 + 验证清单, 看有没有未完成的收尾或验证要求。
- 若改动涉及数据库/歌词/UI, 对应先读 `doc/database.md` / `doc/ui.md`。
- `CLAUDE.md` 里的架构段落, 定位改动应落在哪个文件/extension。

产出: 一句话说明"这次要改什么、落在哪几个文件、有没有相关的已知约束"。

## 阶段 1 · 设计(先对齐再写码)

写一段简短设计(不用长篇):

- 要实现的行为是什么, 用户可见的效果。
- 打算改动/新增哪些文件。新增 Swift 文件放在 `Sources/LocalLrcPlayer/` 下即可, `build.sh` 会按字母序自动收集, 无需改任何清单。
- 关键不变量别踩: 曲目按 SHA256 内容哈希去重(同一段音频跨文件夹只占总播放列表一行); 数据库只做索引, 歌词真相永远是音频旁的 `.lrc` 文件, 不要把数据库当第二份歌词。
- 若动 schema, 说明是否需要新的迁移(当前 v3)。

把设计发给用户确认后再动手。改动小且明确时可只报一句设计然后继续。

## 阶段 2 · 拆步骤

把实现拆成有序的小步, 用 TaskCreate 建任务清单(改动很小时可省略)。每步应可独立验证, 避免"顺手改了不该动的代码"——只动本次目标涉及的范围。

## 阶段 3 · 改代码

- 匹配周边代码风格(AppKit, 不用 SwiftUI; 注释密度、命名、惯用法向邻近文件看齐)。
- 窗口逻辑按职责放进对应 extension(`PlayerWindowController_Library` / `_Playback` / `_LyricsDownload`), 不要都堆进主文件。
- 每张表的读写走对应 repository, 记录结构体放 `DatabaseModels`。
- 数据安全红线(HANDOFF.md 明令): 不要删除或覆盖用户已有的本地音乐、歌词 `.lrc`、Cookie、缓存文件。这些是用户资产, 数据库只是索引。

## 阶段 4 · 构建 + 真机验证(本项目硬约束)

没有热重载。必须:

1. 退出正在运行的 App(如果开着)。
2. 运行 `./build.sh` 重新编译 + 打包 + 临时签名。
3. `plutil -lint build/LocalLrcPlayer.app/Contents/Info.plist` 校验 Info.plist(HANDOFF.md 验证清单要求)。
4. `open build/LocalLrcPlayer.app` 打开验证。

构建用 `-O`。FLAC 精确 seek 依赖 `/opt/homebrew/bin/ffmpeg`。如果改动能观察到界面/播放行为, 就实际打开 App 看一眼, 不要只凭"编译过了"就说完成。

## 阶段 5 · 跑测试

`./test.sh` 会把所有源文件(去掉 `main.swift`)+ 测试文件编译成一个二进制运行, 然后再调 `build.sh`。测试聚焦 SQLite 仓储逻辑(内容哈希去重、总播放列表累积/排序、播放状态持久化、设置/迁移默认值)。

- 若你改了数据层, 优先在 `Tests/RunDatabaseTests/main.swift` 补一个断言(harness 是手写的 `assertEqual`/`assertTrue`, 末尾 `do{...}catch{exit(1)}` 作 runner)。
- 想只跑某个测试, 就把末尾 `do` 块里其他调用注释掉。

## 阶段 6 · 更新文档(动完必做)

按需同步维护(别用 `**bold**`, 本仓库 .md 不用粗体), 遵循 HANDOFF.md 的文档分工 —— 每类信息只写一处:

- `CHANGELOG.md` —— 按日期记录这次完成的工作(今天日期从会话上下文取, 摘要级不逐条复述 diff)。
- `ROADMAP.md` —— 若完成了计划项就勾掉; 若发现新 bug 就登记到 Known Bugs。
- `README.md` —— 若新增/改变了用户可见功能或用法, 更新它(功能与使用方式的真相来源)。
- 若行为变了, 同步 `doc/database.md`(表结构/读写) / `doc/ui.md`(主窗口 UI 约定)。
- 不要动 `HANDOFF.md` —— 那里只放不会过期的协作流程, 不放本次功能记录。

## 收尾报告

按 HANDOFF.md 里的 Handoff Template 格式输出交接记录(本次目标 / 修改文件 / 实现内容 / 验证 / 文档更新 / 未完成风险), 不要另编格式 —— 交接格式的真相来源是 HANDOFF.md。构建/测试结果如实写, 失败就贴原因。提交/推送只在用户明确要求时做。
